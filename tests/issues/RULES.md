# 议题管理规则

## 保存位置

议题、管理规则、索引和验证记录统一保存在 `aleph-tests/tests/issues/` 中。工作区根目录的 `AGENTS.md` 提供维护入口。议题维护不得修改主工作区 `/home/paulus-chang/项目/aleph`，也不得把相关文件复制到主工作区。

## 当前状态

每条议题在同一时间只能有一个当前状态。议题文件开头的 `status` 字段是当前状态的唯一记录位置，字段必须是单个字符串。正文中的验证记录、历史说明和远端链接不构成额外状态。

| 状态 | 含义与设置条件 | 维护方式 |
| --- | --- | --- |
| 可疑 | 代理发现了问题或功能缺项，但尚未获得符合下列验证要求的证据。源码检查、会话线索和未经复跑的旧结论可以作为线索。 | 代理可以创建并补充线索。 |
| 自动测试证实问题 | 已构建可重复的测试样例，自动运行当前代码后，结果明显违反预期。必须保存测试位置、执行命令、被测版本、实际结果和预期结果。 | 代理可以依据实际测试结果设置。 |
| dsh实测有问题 | 已在实际 DSH 环境复现议题所描述的问题。必须写明环境、操作、观察结果和实测范围。测试替身和源码检查不能替代 DSH 实测。 | 代理可以依据实际复现记录设置。 |
| 已上传 | 议题已发布到远端。应记录远端链接；用户明确告知已上传但未提供链接时，可以设置该状态，同时注明链接待补充。 | 用户手动维护；代理仅在用户明确要求时代改。 |
| 本地在尝试解决 | 本地正在尝试解决方案，相关工作尚未完成。应记录尝试方案、工作区或分支、当前结果和剩余工作。 | 用户手动维护；代理仅在用户明确要求时代改。 |
| 已解决 | 已有相关解决方案的拉取请求，提交者可以是用户或其他贡献者。应记录拉取请求链接及解决范围。 | 用户手动维护；代理仅在用户明确要求时代改。 |

“已解决”按本规则表示已有相关解决方案的拉取请求，并不自动表示该请求已经合并或通过复测。合并情况和复测结果写入正文。仅有本地改动、测试通过或远端议题关闭，都不能擅自设置“已解决”。

状态表示当前维护进展，不要求依次经过所有状态。例如，议题可以从“可疑”进入“dsh实测有问题”，随后进入“已上传”。状态变更后必须保留已有测试证据，不能用新状态替代验证记录。

代理可以依据新证据调整“可疑”“自动测试证实问题”“dsh实测有问题”。进入用户手动维护的状态后，代理只能补充证据，不能因新增测试结果擅自覆盖当前状态。用户明确要求更新状态时，代理应记录更新依据。

功能缺项也使用上述状态。没有可重复的自动测试或实际 DSH 复现记录时，功能缺项先使用“可疑”；该状态不表示功能建议被撤回。已有会话模拟但缺少可在本工作区复跑的测试时，先保留模拟线索，补齐验证后再改状态。

## 重复内容与合并

**不能有内容相近的处于同一状态的超过一条 issue。**

新增议题或修改状态前，必须阅读索引并搜索已有议题的标题、触发条件、影响和期望行为。判断依据是实际内容，不能只比较标题。

- 如果已有议题覆盖相同问题，应在原文件补充场景、证据或验收条件。
- 如果同一状态下的相近议题可以合并，应保留信息较完整或已经被引用的文件，把其他文件的有效内容并入该文件。
- 合并后删除重复议题文件，在保留文件和索引中记录旧编号及合并去向。合并不是新增状态，不得创建“已合并”状态。
- 不得通过改标题、更换编号或随意修改状态规避重复检查。同一个问题应沿用同一个文件更新状态；不同状态下的相近议题确有独立用途时，必须写明保留原因及内容区别。
- 不同功能可以分别记录，但必须有各自明确的范围和验收条件。持续调度、结果报告和人工控制分别处理不同操作，不应把同一项验收要求重复写成独立议题。

## 文件与编号

独立议题文件使用 `编号-英文简述.md` 命名，开头包含下列字段：

```yaml
---
id: ALEPH-编号
status: 可疑
type: 缺陷
remote_issue: null
pull_request: null
---
```

`type` 用于区分“缺陷”“功能缺项”“缺陷与功能补全”，不表示状态。没有远端链接时使用 `null`，并在正文说明待补信息。

编号创建后保持稳定，允许编号不连续。已合并或删除的编号不再分配给其他议题。索引只记录文件入口和编号关系，不重复保存当前状态，避免出现互相矛盾的状态记录。

## 正文要求

正文应使用简单、具体的语言，至少说明当前情况、影响、期望行为、验证证据或待验证内容，以及验收条件。

缺陷应给出触发条件和实际错误。功能缺项应说明当前缺少的操作及补齐后的行为。自动测试证据必须能复跑，测试失败必须来自议题对应的行为断言；依赖缺失、测试脚本异常或环境故障不能证明产品存在缺陷。

使用测试替身时必须说明替代范围。接口实测与页面实测应分别记录；只检查过客户端源码时，不能宣称已经在浏览器中复现页面问题。普通测试模式中的已知缺陷标记不能作为验证依据，相关测试应使用严格模式执行。

每次维护后应检查：当前状态是否合法且唯一、相近内容是否重复、文件链接是否有效、证据是否支持当前状态，以及手动维护状态是否获得明确指令。议题上传、代码提交、分支推送和拉取请求创建均按用户的明确指令另行执行。
